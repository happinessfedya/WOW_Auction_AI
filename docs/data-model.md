# Независимая модель данных

## Фактическая схема knowledge, этап 3

Отдельная `.private/knowledge.sqlite3`, application ID `0x57414B33`, schema 1. Исходные книги активов/рынка не изменяются этим импортом. Приведённые далее сущности последующих этапов остаются проектом.

| Таблица/контракт | Назначение и граница |
|---|---|
| `imports` | Corpus hash, source revision, parser revision, build, manifest, checkpoint, полный знаменатель кандидатов, время получения и наблюдаемой доступности. Незавершённый импорт не заменяет опубликованный; старое возобновление не вправе молча откатить новую версию |
| `entries` | Каждый файл корпуса с hash, конечным disposition, счётчиками/предупреждениями; immutable |
| `candidates` | Неизменяемое source claim с locator, family, applicability, unknowns. Semantic hash отделяет изменения механики от provenance. Статус candidate/historical/unsupported/quarantined не означает confirmed-current |
| `active_sources`, `events` | Указатель выбранной версии и неизменяемая история активации/rollback; исключённые новым корпусом записи остаются в предыдущей версии |
| `research_jobs` | Уникальные запросы на changed subset, недельное обновление, patch и feedback; lease/token/expiry/retry. Очередь исследования не свидетельство состоявшегося AI-анализа |
| `artifacts` | Снимок CraftSim profile/passive DTO, CraftSim cache, TSM item/crafting cache. Identity=raw SHA+normalizer revision+build; payload SHA отдельно. Первый receive/mtime неизменны, текущая свежесть оценивается заново; персональные данные остаются локально |
| `corrections`, `correction_heads` | Предложение с доказательствами и его отдельно проверенное наложение; смена исходной версии лишает старое наложение применимости, rollback не удаляет историю |
| `validate_mechanic` | Целочисленные физические партии/входы/совместные выходы; десятичная probability задаётся явно и полная joint PMF суммируется точно. Mean yield находится в другом поле, отсутствующая PMF не становится равномерной |

Готовность полей механики не даёт права рекомендовать сделку: этап 4 ещё должен проверить рынок, капитал, риск, ограничения и модель исполнения. Данные CraftSim и шаблонов TSM не расширяют автоматически ликвидный капитал этапа 1.

Дата: 2026-10-26. Таблица доменных сущностей ниже описывает целевую систему; физически реализованы локальное хранилище этапа 1, отдельное рыночное хранилище этапа 2 и knowledge-хранилище этапа 3. ## Изменение идентичности рынка без Blizzard

Числовые `realm_id/connected_realm_id` nullable и не нужны для запуска, импорта или ключей доменной модели. UE сообщает собственную группу миров: `kind=provider_connected_realm`, `provider=undermine`, `game=retail`, `region`, упорядоченные уникальные `realm_slugs`, `provider_group_key` SHA-256 канонической идентичности. Поле `membership_effective_at=null`: timestamp цены не выдаётся за дату изменения группы. Снимок хранит raw hash, времена получения/доступности и происхождение утверждения. Различное членство даёт другую версию ключа и требует согласования; разные источники не объединяются автоматически.

TSM realm CSV имеет `kind=realm_unresolved` и собственный `(provider, region, realm_slug)`: это пригодные агрегаты этого источника при неподтверждённой межисточниковой связи. Региональный summary остаётся `region_aggregate`; commodity — `commodity`. Неизвестное числовое ID не превращается в 0, а `offer_ordinal` Undermine — в auction ID.

Физическая рыночная схема: `policies`, `snapshots`, `current_datasets`, `http_validators`, `attempts`, `jobs`, `rate_usage`, `provider_cooldowns`, `gaps`, `input_references`. Старая таблица `realm_mappings` сохранена для совместимости первой миграции и не используется рабочим resolver. Отдельная БД имеет application ID `0x57414D32`, версию 3: migration1→2 добавляет cooldown, migration2→3 — `http_validators` и clock descriptor. Принятая база активов не переписывается.

`received_at_ns` — окончание HTTP-чтения, `available_at_ns` — отдельная публикация после commit. Повторный hash/304 при той же нормализации не обновляет возраст старого содержимого; новая версия получает новый snapshot. `normalizer_revision` — fingerprint исходников common/freshness/adapter/worker: при его смене conditional reuse отключается, пакет повторно загружается, новая проекция не затирает старую и не меняет source scan time. Source scan/generated/lastSeen и границы исторической публикации различаются. Сломанный/частичный пакет не заменяет last-good; отсутствие доступного содержимого после retention не маскируется сохранённым hash. Provider cooldown хранится отдельно от job: 429 запрещает раннюю попытку другим job того же источника и переживает restart/force.

`snapshots.freshness_descriptor` сохраняет часы, семантику и scope hash после удаления содержимого, не цены. Регрессия/утрата известных source clocks не заменяет current; equal-time correction разрешена как новая ревизия. `cache_available` означает наличие опубликованного неистёкшего payload; `usable` дополнительно требует complete и подтверждённой source freshness. В `report` пригодность capabilities зависит также от health и наступившего refresh. History/reference/zero quantity не выдаются за current prices. Политика возраста и исключения описаны в [ответе S2-01](review-responses/stage-2-r1-response.md).

HTTP validators принадлежат точному snapshot + normalizer revision + generation и меняются в одной транзакции с current. Отсутствующий header нового 200 очищает соответствующий validator; поля jobs больше не источник HTTP-кэша. 304 сравнивает фактически отправленный conditional context с текущим и проверяет lease, не меняя старые received/available/expiry. После crash metadata восстанавливаются из committed snapshot; неподтверждённый 304 планирует full fetch с backoff.

## Общие правила

Деньги в целых copper (`10000 copper = 1 gold`); исходная точность и округление сохраняются. Ожидания могут быть Decimal/рациональными числами, но остатки и исполненные количества целые. Не использовать binary float для денег. Неведомые значения — nullable с причиной, ноль — наблюдённый ноль. События append-only; исправления ссылаются на предыдущую запись. Импорт и построенные проекции разделены.

Пять независимых времён: `event_at` (момент события, если известен), `observed_at` (когда источник его увидел), `source_snapshot_at`, `received_at`, `available_at` (когда запись прошла проверку и стала доступна решению). Продажа и получение почты не один момент; TSM time может быть оценкой события из срока письма, с отдельными semantics/precision, а неизвестный event_at остаётся null. Дополнительно `valid_from/to` для механики и `recorded_at` для истории знания. Часы UTC, отображение Europe/Moscow/выбранный пояс, неопределённость часов хранится. Отсутствующий timestamp не заменяется mtime без метки `file_time_proxy`. **Нет универсального фильтра для всех исторических режимов:** actual prospective/exact original knowledge требует available_at≤decision_at; условная реконструкция использует отдельный PublicationAvailabilityClaim без изменения фактических времён. Полные контракты: [T2-C01–C04](research/temporal-evaluation-r2.md).

`EvaluationRun.mode` задаётся до прогона: `recorded_decision_replay`, `deterministic_recompute`, `public_history_reconstruction`, `llm_historical_exploration`, `prospective_evaluation`. Первые два используют исходный DecisionInputManifest и stored LLM output, не новый запрос к модели. Новый modern-LLM исторический запрос получает exploration и model_knowledge_status=unverified, даже если все внешние данные прошли временной фильтр. Реконструированная готовность = max(доказанная верхняя граница публикации точной ревизии, готовность зависимостей, конец final aggregate period при наличии) + upper bound моделируемой задержки обработки. Неизвестная обязательная граница исключает вход из основного reconstruction run; допущение допускается только в отдельно маркированном сценарии. В интервальном времени сравниваются верхняя граница готовности и нижняя граница решения.

`file_written_at` хранится отдельно: proxy времени файла не повышает свежесть/приоритет наблюдения контейнера, если время его осмотра неизвестно. Для BagSync банк остаётся `observed_at=null` даже при новом mtime всего файла.

Каждое наблюдение хранит `source_id`, исходный ключ, hash/разрешённый payload locator, parser/schema/addon version, game build, статус доказательства, область полноты, срок хранения и причину недоступности. Числовая уверенность модели не заменяет категорию доказательств.

## Связи, которые нельзя потерять

`Forecast → DecisionSnapshot/DecisionInputManifest → сохранённые версии источников/механик/стратегии/исполнения/visible LLM IO` позволяет replay в пределах наличия артефактов и наследует исходный temporal grade. `TransformationVersion → Input/Outcome/Constraint → ItemVariant/Resource` задаёт гиперграф. `VirtualEvent → Forecast → ExecutionAssessment` отличает рекомендацию от предполагаемого исполнения. `KnowledgeRevision → affected transformations → impacted forecasts` не переписывает прежние прогнозы, а добавляет ретроспективную пометку. `RealLedgerEvent → CostLot → ManualLink` сохраняет неизвестность связей, не создавая ложной точной прибыли. `UnexplainedCase → ObservationRequest → FactorCandidate → FactorExperiment → StrategyVersion` расширяет модель без тайной правки main. `Position → origin episode + versioned management assignment` сохраняет происхождение и себестоимость при смене менеджера.

## Дедупликация, оценки имущества и себестоимость

Ключ баланса: `(account scope, owner, container, item variant, observation generation)`. Account scope — подтверждённая группа общей собственности/регион, не просто папка SV или отдельная WoW-лицензия; связь нескольких лицензий с одним warband требует явного подтверждения. Согласование выполняется отдельно для cash/bag/bank/warband/auction/mail, с историей выбора. Контейнеры, которые аддон уже агрегирует, нельзя суммировать с их детализацией. Перемещение с задержкой снимков создаёт неоднозначность: общий капитал показывается диапазоном/неполным, а не сложением обоих мест.

Товарные запасы требуют классификации пользователя/правила торгуемости; экипировка исключается автоматически из торговли, BoP не ликвидный актив. Текущая котировка, консервативная стоимость реализации и историческая себестоимость — три разных показателя. Остатки суммировать только при совместимом срезе; на экране есть время каждого источника и неосмотренные хранилища.

Предложение для виртуальной книги: явные cost lots и FIFO как первая воспроизводимая политика, с конфигурацией/версией. Для реальной книги сначала точные доступные связи TSM, затем ручная связь; не достраивать неизвестную закупочную цену. Совместные продукты преобразования требуют отдельной политики распределения затрат; до её выбора прибыль считать по всей партии, а не оптимистически обнулять побочный продукт. Денежные взносы/изъятия в виртуальный портфель меняют капитал, не доходность.

## Варианты хранения и ограничение объёма

SQLite — метаданные, нормализованные рабочие выборки, очередь, портфели. Исходные HTTP/SV-пакеты — только в приватном разрешённом хранилище с правами и сроком хранения. Историю рыночных уровней делить по scope/дате, индексировать item/time; не обещать многолетние миллионы лотов в одном маленьком файле. На этапе 2 измерить `bytes/snapshot × snapshots/day × scopes × retention`, время импорта и размер БД с DELETE journal; переоценка относится к этапу 4. Агрегация не заменяет уровни для replay; если уровни удалены, это ограничение воспроизводимости видно пользователю.
