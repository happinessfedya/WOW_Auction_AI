# Этап 1: запуск и независимая проверка

26.10.2026. R2 этапа 0 принят пользователем в чате; разрешён только этап 1.
Команды ниже запускаются из корня проекта в PowerShell. Они не запускают WoW,
не вызывают `/reload`, не меняют аддоны и не обращаются к платным API.

## Окружение

Проверено на Windows 11, Python 3.13.7, встроенной SQLite 3.50.4. Внешних
Python-зависимостей нет. Локальное окружение создаётся без pip:

```powershell
python -m venv --without-pip .venv
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Обычный `venv` с ensurepip в этой среде завершился ошибкой; `--without-pip`
успешен. Системный Python не изменён. `pyproject.toml` фиксирует проверенные
версии; это запуск модуля из checkout, не установка пакета через pip.
Поддержка других версий Python 3.12+ заявлена как целевая, но здесь не тестировалась.

SQLite использует **DELETE journal, synchronous=FULL**, сериализованные транзакции
записи и timeout 5 секунд. WAL-база отклоняется. Это разрешённый безопасный режим
T1-10: найденная SQLite не объявляется исправленной. Основание ограничения WAL
сохранено в [E-TECH-01](research-evidence.md) и [официальной документации SQLite](https://www.sqlite.org/wal.html).
Повторное сетевое чтение этой страницы при этапе 1 не удалось; новая версия
SQLite не загружалась. WAL требует отдельной проверки исправленного runtime.

## Первое подключение и чтение

```powershell
.\.venv\Scripts\python.exe -m wow_auction init --wow-root 'W:\Battle.net\Games\World of Warcraft\_retail_' --region EU
.\.venv\Scripts\python.exe -m wow_auction scan
.\.venv\Scripts\python.exe -m wow_auction status
```

В этой рабочей папке подключение уже выполнено: повторный `init` намеренно не
перезаписывает конфигурацию. Путь к игре передаётся параметром, не зашит в
программу. `init` проверяет только `WTF/Account/*/SavedVariables` и четыре
известных имени файлов, исключая `.bak`; каталоги авторизации не читаются.
Регион EU передан по исходному заданию пользователя, не угадан из имени папки.
Имена миров/персонажей берутся из источников; числовые realm/connected-realm IDs
появятся на этапе 2 после проверки справочника.

`.private/config.local.json` содержит абсолютные локальные пути, псевдоним
`account_scope`, регион, `ownership_group` и расположение базы. Конфигурация,
исходные приватные снимки внутри базы и резервные копии исключены из Git.
SQLite не шифрует их: защита на диске соответствует правам локального каталога
Windows. Не публикуйте `.private/` вместе с отчётом и не добавляйте API-ключи в
эту конфигурацию — на этапе 1 они не нужны.

`account_scope` объединяет файлы одной папки, но не доказывает независимость
банков нескольких лицензий. Оставленный `ownership_group=null` означает
неизвестное межаккаунтное владение. После подтверждения пользователем одна
и та же строка группы задаётся всем аддонам соответствующих лицензий; различным
подтверждённым владельцам — разные строки. Регион/группа должны совпадать у всех
источников одного scope. Изменение этих настроек требует `scan`; старые версии
сохраняют первоначальные метки. Без нового импорта статус `requires_reimport`.

Уточнение неизвестного региона при неизменных bytes не создаёт вторую операцию.
Смена известного региона либо смешанная старая проекция дают
`ledger_context_status=requires_resolution`: неподтверждённый контекст виден даже
при следующем `unchanged`, scan/ограниченный watch завершается кодом 2.
Возврат настройки не разрешает конфликт автоматически. Эти случаи отдельно
проверены при исправлении [S1-01](review-responses/stage-1-r1-response.md).

Обычный `status` выводит количество записей, hashes, свежесть файлов, ошибки,
пробелы и отсутствие полной прибыли. Для просмотра собственных сумм в медных,
имён, отдельных хранилищ и операций **только локально**:

```powershell
.\.venv\Scripts\python.exe -m wow_auction status --details
```

10000 copper = 1 gold. `observed_cash_copper` — сумма выбранных наблюдений
разного времени; это не текущий NAV, не доход и не виртуальные деньги.
Неизвестность владения/идентичности может сделать сумму `null`.
`current_nav_copper` и полный `real_pnl_copper` остаются `null`: цены,
торгуемость, себестоимость и все расходы сейчас не подтверждены.
Время каждого GX-наблюдения отдельно; mtime BagSync не заменяет неизвестное
время осмотра банка. Пустая сохранённая таблица не означает доказанный полный
осмотр. Предметные копии/конфликты видны в подробной проекции.

## Наблюдение за файлами

```powershell
.\.venv\Scripts\python.exe -m wow_auction watch --interval 10
```

Это явный foreground-процесс; остановка — Ctrl+C. Служба/автозапуск не
устанавливались. Он работает с закрытой игрой, но новые игровые данные
появляются только после фактической записи SavedVariables самой игрой.
Для ограниченной проверки: `watch --interval 1 --cycles 2`.
Файл читается дважды, с паузой 0.1 секунды, сравнением bytes, размера, mtime и
идентичности файла. Возможная последующая запись не объявляется исключённой.
Пауза настраивается в `settle_seconds` (0–10 секунд). Повторные опросы неизменных
байтов не создают второй баланс/операции и не омолаживают исходные значения.

Лимиты безопасности parser: 32 MiB на файл, глубина 80 (не более 100 при
изменении ParseLimits), миллион узлов, 8 MiB на строку, 128 символов на число,
5 секунд разбора. Ledger отдельно ограничен 32 MiB CSV, 400000 строк и 4096
символами поля. Это открытые технические лимиты, не торговые ограничения.
Недопустимая схема/UTF-8/Lua expression/нестабильная запись — карантин, без
потери последнего валидного снимка. Повтор повреждённого файла не дублирует его
raw blob. Журнал опросов сохраняется; автоматическое удаление истории в этом
этапе не вводилось. Рост больших/длительных историй ещё не измерен.

## Восстановление

```powershell
.\.venv\Scripts\python.exe -m wow_auction backup .private\review-backup.sqlite3
.\.venv\Scripts\python.exe -m wow_auction restore .private\review-backup.sqlite3 .private\review-restored.sqlite3
```

Имена назначения должны быть новыми. Резервная копия создаётся через SQLite
backup API и проверяется `integrity_check`, а не копированием файла активной БД.
Восстановление создаёт отдельную книгу и проверяет/мигрирует её; текущая
конфигурация не переключается автоматически. Чтобы проверить копию, измените
поле `database` в отдельной копии конфигурации и передайте `--config <путь>`
**перед** именем команды. Исходная резервная копия не изменяется.
Запись базы/резерва в объявленный каталог WoW и в `.lua`/`.bak` запрещена.

Снимок, Ledger state, revisions и checkpoint фиксируются одной транзакцией.
`available_at_ns` публикуется отдельной отметкой **после** durable commit.
При аварии в промежутке запись pending; следующий запуск присваивает более
позднюю доступность, не повторяя события. Для этой консервативной границы
есть тест принудительного завершения процесса. Это не обещание точного replay
будущего торгового движка, который появится на этапе 5.

Схема имеет версии 1→2→3 с checksum миграций. Третья добавляет историю проверки
ручных связей и решения о контексте, сохраняя исходные таблицы и записи.
Чужая, более новая, повреждённая
или WAL-база не принимается. Автоматического destructive reset нет.

## Исправление контекста уже сохранённой книги

После явной проверки, что вся история одного источника относится к выбранным
в конфигурации account scope и региону, можно выполнить:

```text
python -m wow_auction rebuild-ledger-context SOURCE_KEY --backup .private/context-before.sqlite3 --reason "Основание исправления региона всей истории источника"
```

Source key доступен в status. Регион должен быть задан явно. Backup обязателен,
имя назначения должно быть новым; состояние после backup проверяется перед
изменением. Команда читает сохранённые raw snapshots, атомарно перестраивает
только текущую проекцию и записывает основание/hash backup. Исходная история
не удаляется, новые финансовые события не создаются, зависимые ручные связи
требуют проверки. При отказе до commit остаётся прежняя проекция и созданная
резервная копия. Сбой после durable commit не отменяет сохранённую новую проекцию:
незавершённая публикация доступности восстанавливается общим postcommit recovery.

Этой командой нельзя объединять действительно разные региональные книги:
они должны быть отдельными источниками. Это явное исправление сведений об одной
истории, не автоматическое сопоставление похожих сделок. После перестроения
`effective_ledger_changes` содержит действующий поток изменений; исходный
`ledger_changes` сохраняет также прежние, уже заменённые пакеты для аудита.
Baseline восстановленной проекции не торговое событие. Команда доступна для
исправления выявленной проблемы, но на рабочей БД этого пользователя не запускалась.

## Ручная связь операций

```text
python -m wow_auction link SOURCE_KEY BUY_CANONICAL_ID SALE_CANONICAL_ID QUANTITY --note "основание связи"
```

IDs доступны в `status --details`. Связь сохраняется отдельно от TSM;
количество ограничено остатком распределения наблюдаемых buy/sale строк.
Исправление — новая запись с `--supersedes-id`, прежняя не исчезает. Связь не
доказывает одинаковую себестоимость преобразованных предметов и не делает
полный P&L известным: потери залога, дополнительные расходы и механика остаются
отдельными неизвестными. В текущем реальном Ledger есть покупка и ремонт,
но нет продажи для buy→sale связи; этот сценарий остаётся непроверенным на
реальных данных, его синтетический тест обязателен.

Связь привязана к проверенным ревизиям операций. При изменении количества,
ревизии, контекста, исчезновении/неопределённости endpoint она получает
`requires_review` и исключается из подтверждённых распределений. Повтор не
сбрасывает этот статус; новые данные не обрезают количество старой связи.
Обычный status показывает счётчики состояний, `--details` — причины и историю.
Для явного отзыва с сохранением первоначального решения:

```text
python -m wow_auction unlink SOURCE_KEY LINK_ID --note "Основание отзыва"
```

Связи старой схемы без привязки к ревизии не считаются автоматически
подтверждёнными после миграции; их можно явно заменить или отозвать.

Пакет дополнен сквозным тестом
`IngestionTests.test_delayed_savedvariables_purchase_and_repair_reconcile_without_duplicates`:
до обновления файлов Ledger пуст, после появляется покупка и ремонт, расход
совпадает с GX/BagSync, повтор не дублирует деньги/события. Последний полный
прогон исходного пакета — 122/122 PASS. Результат нового комплекта после
аудита находится в [ответе R1](review-responses/stage-1-r1-response.md) и
[JSON доказательств](stage1-r1-fix-evidence.json). Это синтетический тест приложения; реальный игровой
опыт описан отдельно выше.

В этой рабочей папке сохранены приватные исходные слепки и процедура их
повторной проверки, без обращения к действующим игровым файлам:

```powershell
.\.venv\Scripts\python.exe .private\verify_stage1_saved_probe.py
```

Процедура создаёт новую книгу в `.private/stage1-real-validation/`, сравнивает
импорт до/после, повтор и восстановление, а рабочую БД проверяет только чтением.
Она не входит в публичный пакет вместе с персональными слепками; без этих
локальных материалов реальная проверка не объявляется воспроизведённой.
Время нового воспроизведения не подменяет исходные даты захвата.

Пользователь уже подтвердил вход на основных персонажей и открытие их
сумок/банков для BagSync. Суммы GX/BagSync согласует приложение; переписывать
их вручную или повторять обход сейчас не требуется. После последующего опыта
с включённым TSM импортированы реальная покупка за 100 меди и ремонт за
27084 меди; уменьшение кошелька GX/BagSync совпало с суммой 27184 меди.
Четыре файла приняты, повторный импорт дал 4×unchanged. Остальные четыре
семейства Ledger пусты; продажи, возвраты, переводы и реальное изменение
существующей агрегированной строки этим опытом не проверены.

Специально покупать товар, включать GX autosave или переустанавливать аддоны
не требуется. По мере появления новых записей повторять импорт и проверять
net/quantity/time, расходы и переводы по доступным данным. Различать время
события, сохранения и захвата: почтовое время покупки вычислено TSM из срока
жизни письма, `saveTimeBuys` — метка сохранения, отдельного времени получения
вложения в этих данных нет. Непроведённые сценарии остаются PARTIAL/BLOCKED
DATA и не выдаются за успешные интеграции. Следующий этап не запускается
автоматически.
