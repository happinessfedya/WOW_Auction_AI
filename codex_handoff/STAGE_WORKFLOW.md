# Как работать с двумя Codex

## Схема

1. Основной Codex получает исходное большое ТЗ и `MAIN_CODEX_CORRECTION.md`.
2. Завершает **один** этап, создаёт/обновляет документы, фиксирует изменения и предоставляет краткий отчёт + команды проверок.
3. Независимый Codex-проверяльщик получает репозиторий, `PROJECT_CONTEXT.md`, `INDEPENDENT_REVIEWER_PROMPT.md` и отчёт разработчика.
4. Проверяльщик возвращает `ПРИНЯТ` / `НЕ ПРИНЯТ` / `ЗАБЛОКИРОВАН ВНЕШНИМ УСЛОВИЕМ`, доказательства и адресное следующее задание.
5. Пользователь решает, принимать ли этап. Только после этого разработчик начинает следующий.

## Сообщение разработчику после окончания любого этапа

«Остановись на текущем этапе N. Сделай короткий отчёт: список изменённых файлов/коммит, критерии приёмки, команды и результаты тестов, примеры реальных полученных данных с удалением секретов, непроверенные предположения, остающиеся риски. Следующий этап не запускай; материалы будут переданы независимому аудитору».

## Сообщение проверяльщику

«Проверь этап N по критериям из проектного контекста. Не доверяй отчёту разработчика без воспроизведения. Твоя главная зона внимания — [наиболее рискованный аспект этапа]. Предоставь доказательства, вердикт и адресный промпт разработчику. Не изменяй рабочую ветку».

## Если проверка провалена

«Этап N не принимаю. Исправь только перечисленные проверяльщиком доказанные дефекты и добавь регрессионные тесты. Для вероятных, но неподтверждённых причин создай диагностическую процедуру; не меняй торговую логику на догадках. Не переписывай работающие модули и не переходи к N+1. Повтори приёмочные тесты и подготовь новый отчёт».

## Если проверка прошла

«Этап N принят после независимой проверки. Переходи к этапу N+1 строго по `docs/implementation-plan.md` и исходным требованиям; исправления за рамками этапа не предпринимать без обоснования. Сохраняй регрессионные тесты и разделение фактов/гипотез. По завершении остановись и предоставь отчёт для проверки».

## Если есть блокировка внешним источником

«Этап N заблокирован [точное условие]. Не изображай успешную интеграцию. Сохрани независимый тест/фикстуру, перечисли, что именно необходимо (например, API-ключ с ограниченными правами, сохранённый файл, запуск WoW для расчёта CraftSim), и какие задачи могут быть безопасно выполнены без этого. Не переходи к зависимому этапу».

## На что особенно смотреть по этапам

- **0:** доказательства по API, Lua, систематическая архитектура и план независимой диагностики экономической логики.
- **1:** правильные деньги/банки/персонажи/дубли/давность, чтение файлов без воздействия на игру.
- **2:** часы снимков, региональные/серверные цены, глубина предложения, лимиты, разрыв между снимком и фактом сделки.
- **3:** широта и доказанность не только профессий, но и обменов/контейнеров, патчевых ограничений, случайных выходов.
- **4:** ожидаемая прибыль и риск, затраты и циклы, размер позиции и ликвидность, отсутствие произвольной целевой доходности.
- **5:** prospective vs retrospective, фиксация прогноза до исхода, отсутствие look-ahead, честная неопределённость исполнения.
- **6:** **логические ошибки модели**, проверяемые гипотезы, контроль переобучения, shadow strategies, отсутствие ложного объяснения.
- **7:** наглядность, настраиваемость ИИ, источники и свежесть, отзыв на ошибку, тесты UI и работа при закрытом WoW.
