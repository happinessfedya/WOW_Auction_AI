## 2. T2-C01 — пять разных режимов, без смешения результатов

Каждый `EvaluationRun` обязан иметь `mode`, `data_time_basis`, `model_knowledge_status`, `decision_origin`, `original_run_id`, `result_claims`, `limitations`. Режим задаётся **до** прогона; фильтр доступности выбирается по нему. Успешная арифметика не может автоматически повысить класс доказательств.

| Mode | Что выполняется | Допустимые входы и ИИ | Допустимое заявление / запрет |
|---|---|---|---|
| `recorded_decision_replay` | Восстановление уже сохранённого решения, его пакета входов, версий, видимого ответа ИИ и причин | Только исходные разрешённые сохранённые артефакты. **Нового вызова LLM нет** | «Такое решение было сохранено с такими входами». Не новая проверка способности прогнозировать; повтор наследует temporal grade оригинала. Если оригинал был современным ретроспективным LLM-прогоном, replay не делает его чистым |
| `deterministic_recompute` | Повтор арифметики/признаков/ограничений исходной версии, сравнение с сохранённым результатом | Те же hashes входов, код/конфигурация/зависимости, RNG seeds при наличии; сохранённый ответ ИИ как фиксированный вход | «Детерминированная часть воспроизводится / расходится». Не повторное мышление модели. Новый код или иные inputs создают отдельный диагностический run, не заменяют оригинал |
| `public_history_reconstruction` | Условный backtest алгоритма на сведениях, доступных публике к моделируемому времени, хотя приложение загрузило их позже | Отдельное подтверждение доступности **конкретной версии** по T2-C03; алгоритм без нового вызова современной LLM. Все стратегии/признаки имеют даты разработки и явную OOS-политику | «Условная историческая реконструкция при указанных основаниях/задержках». Это не фактическая история знаний приложения. Не означает, что стратегия была разработана в прошлом, и не снимает selection bias |
| `llm_historical_exploration` | Новый вызов сегодняшней LLM для старого периода, включая условную реконструкцию внешних данных | Внешние inputs можно ограничить по времени, но `model_knowledge_status=unverified` по умолчанию; контекст/источники всё равно изолируются | «Историческое исследование с непроверенной временной чистотой модели». Не строгий point-in-time результат; исключён из валидного promotion evidence и агрегированных promotion metrics. Допустимо формировать гипотезы, которые затем проверяются на ещё не увиденном будущем |
| `prospective_evaluation` | Решение и количественный прогноз фиксируются в реальном ходе времени до целевого исхода | Реально принятые к тому времени данные, известная на момент решения версия контекста/знаний, запрос и ответ ИИ полностью зафиксированы; commit до target outcome | «Проспективный прогноз, сохранённый до исхода», с оговорками исполнения/неопределённости часов. Не гарантия будущей прибыли или причинности |

`recorded_decision_replay` и `deterministic_recompute` относятся к уже существовавшим решениям; они не выбирают новый удобный набор inputs через текущий запрос к источнику. Если часть артефактов законно удалена по retention или недоступна, результат `replay_incomplete` с перечнем утраченного. Hash без содержания подтверждает идентичность при повторном наличии, но не восстанавливает входы.

Новая современная LLM в историческом backtest **всегда переводит его в `llm_historical_exploration`**, пока отдельно не установлен доказательный контракт temporal model provenance. Наличие старой модели, опубликованной до события, может дать основание для отдельного исследования, но одного названия/cutoff недостаточно: нужны точная версия, история fine-tuning/RAG/контекста и доступные тогда инструменты. В этом проекте такая сертификация не установлена и не нужна для этапа 0. Обучать свою модель не предлагается.

## 3. T2-C02 — фактическое знание приложения остаётся неизменным

Существующие времена не объединяются: `event_at`, `observed_at`, `source_snapshot_at`, `received_at`, `available_at`. Последнее — фактическое время, когда приложение проверило запись и разрешило её использование. Поздняя загрузка не меняет эту дату на время события/публикации. Если временное окно часов неопределённо, хранится интервал, а не фиктивная точность.

Для новой prospective рекомендации с cutoff `t`:

`eligible_actual(x,t) := x.available_at <= t AND revision_eligible(x,t) AND validation_passed(x) AND scope_compatible(x)`.

При интервалах используется доказанная верхняя граница доступности и нижняя граница cutoff. Null не проходит условие. Более поздняя исправленная версия исходной записи не подменяет исходную. Ранее неизвестный патчноут/механика может объяснять ошибку позже, но не добавляется задним числом в прогноз.

Для exact replay используется запечатанный `DecisionInputManifest` и исходное `available_at`, а не новый отбор «лучших» данных. Ошибка исходной валидации показывается как выявленная ошибка воспроизводимого решения, не исправляется внутри его истории.

## 4. T2-C03 — контракт реконструированной публичной доступности

Новая сущность `PublicationAvailabilityClaim` относится к **точной версии/ревизии содержимого**, а не только URL или дате файла. Поля:

- `content_revision_id/hash`, source/endpoint/scope, `publication_evidence_ids` и lineage;
- `public_available_lower_bound`, `public_available_upper_bound` (если известны), семантика bound и uncertainty;
- `basis = contemporaneous_capture / source_revision_log / documented_release_schedule_with_verified_bound / scenario_assumption / unknown`;
- `period_start`, `period_end_exclusive`, `period_timezone`, `aggregation_rule`, dependency revision IDs, `is_final`/provisional;
- отдельно publication latency bounds, proposed collection/validation latency и measurement/evidence для них;
- `claim_created_at`, claim author/version, status/evidence strength; actual `received_at/available_at` исходной записи неизменны.

Временная граница выводится из сведений, которые **содержательно нужны** для строки. Для подтверждённой консервативной реконструкции:

`reconstructed_ready_upper = max(public_available_upper_bound, required_dependency_ready_upper, final_aggregate_period_end) + simulated_ingest_latency_upper`.

`eligible_reconstructed(x,t) := все необходимые bounds известны и обоснованы AND reconstructed_ready_upper <= t AND сохранена допустимая на t ревизия`.

`final_aggregate_period_end` не применяется к обычному мгновенному наблюдению. Для итогового агрегата он обязателен. Задержка обработки не подменяется исторически неизвестной фактической задержкой приложения: это отдельное предположение/контракт симуляции. Если bound задержки не подтверждён, режим называется сценарной реконструкцией с чувствительностью, а не подтверждённым историческим доступом.

Источник со временем снимка 100, подтверждённой публикацией не позже 105 и фактическим `available_at=300`:

- при `decision_at=110` actual знание приложения исключает строку;
- реконструкция может допустить её, если revision/capture evidence соответствует именно этой строке и выбранная latency-upper не больше 5;
- запись `available_at=300` при этом остаётся 300;
- если известен только snapshot100, строка не получает автоматически publication105 или zero lag.

Поздний первый HTTP-ответ в момент 300 даёт лишь верхнюю границу «эта версия была доступна не позже 300»; он сам не доказывает доступность в105. Текущий `Last-Modified`, заголовок/датировка страницы или `lastUpdated` общего файла допускаются только с проверенной семантикой точной ревизии; они не универсальная машина восстановления прошлой публикации. Наличие исторической даты в payload не достаточное основание.

Если верхняя граница публикации неизвестна, консервативный основной reconstruction run строку исключает. Можно выполнить отдельно маркированные сценарии с заранее выбранными задержками/границами и показать чувствительность/долю исключённых входов. Такие сценарии не получают подтверждённый temporal grade и не маскируются одним оптимистическим итогом. Обещание «вся публичная история точно пригодна для backtest» запрещено.

Поздние коррекции/пересчёты создают новую ревизию и новое утверждение доступности. Старую строку можно использовать только если сохранено основание её старого содержания. Нельзя обучать на сегодняшнем исправленном ряде и утверждать, что эта же версия существовала в момент старого решения. Для derived feature дата доступности — максимум дат всех зависимостей и завершения вычисления; настройки нормализации, категорий, universe и политики отбора также версионируются.

## 5. T2-C04 — дневные агрегаты и Undermine

Факт T2-S02 означает зависимость дневного результата от выбранного максимума **всего** периода. Даже если выбранный снимок оказался утренним, узнать, что более высокого количества позднее не будет, в начале дня нельзя. Это проектное следствие определения агрегата, а не отдельное обещание API.

Итоговая дневная точка не допускается в решение до `period_end_exclusive` плюс обоснованная задержка публикации/получения. Если пользовательская дата отображается в Москве, это не меняет source day boundaries. Пока timezone, finalization/revision policy и публикационные bounds источника не подтверждены, корректны исключение из основного реконструированного режима или отдельный сценарий с явной неизвестностью. Произвольные «сутки запаса» могут быть стресс-допущением, но сами по себе не доказывают правильную временную границу.

Например, **синтетический** период [0,86400), итоговый максимум выбран из снимка43200, publication upper=87000, validation latency upper=30: при decision60000 итог недопустим, при decision87020 ещё недопустим, при87030 допустим при прочих проверенных условиях. Внутридневной `max_so_far` мог быть доступен раньше, но это другой признак с собственными dependency IDs и snapshot; его нельзя подменить будущим final daily max.

У daily ряда отсутствуют гарантированные уровни предложения/исполнение; правильный timestamp не превращает его в книгу лотов. У hourly при quantity0 перенесённая старая цена не означает новое предложение; это ограничение сохраняется независимо от temporal mode.

## 6. T2-C05 — изоляция прогнозирования, расследования и памяти

Будущий `PredictorContext` строится из запечатанного набора на cutoff; `AuditContext` может видеть исходы и поздние сведения, но хранится в отдельном namespace/сеансе с отдельными правами чтения/записи. Разделяется не только текст prompt: история диалога, RAG-коллекции, retrieval cache, краткие summaries, долгосрочная память, результаты инструментов и пользовательские feedback records имеют владельца/version/knowledge time.

Правила:

1. Прогнозирующий исторический run не использует неограниченный текущий web search. Инструменты доступны через evidence broker, возвращающий только разрешённые revisions по выбранному time basis. Разрешённые source IDs и результат каждой выдачи сохраняются. Установка prompt без контроля выдачи недостаточна.
2. Аудитор не дописывает итог события или своё объяснение в память исходного PredictorContext. Прямой доступ к audit-only namespace отклоняется до вызова модели. Реализация не полагается на добросовестность LLM.
3. Проверенная новая механика/фактор может быть передана в **будущие** прогнозы после регистрации новой knowledge/strategy версии и её фактического `available_at`. Это не разрешение реконструировать с этим знанием старые решения. Исследование S0-04 проходит те же ворота.
4. Между историческими folds/экспериментами память сбрасывается/изолируется; результаты test fold не входят в training/validation summaries. Один агент, просмотревший test outcomes, не считается «не видевшим будущее» после смены сообщения. Новый session уменьшает явный канал, но не очищает веса LLM.
5. Запрет межконтекстной выдачи проверяется на уровне доступа/manifest. Идентичность провайдера/модели у разных ролей не доказывает независимость; независимость свидетельств по происхождению проверяется отдельно.

Нужные новые DTO: `EvaluationRun`, `DecisionInputManifest`, `PublicationAvailabilityClaim`, `ContextManifest`, `ContextAccessDecision`, `ModelProvenance`, `TemporalValidityAssessment`. Последний хранит отдельно `external_data_status`, `context_isolation_status`, `model_knowledge_status`, `original_decision_temporal_status`, `claim_class`, failure reasons; один boolean «no lookahead» недостаточен.

## 7. T2-C06 — что сохраняется и что можно воспроизвести

На каждое реальное/экспериментальное обращение сохранить разрешённые политикой exact visible request/response, provider, запрошенный model ID и фактически возвращённый snapshot/version если доступен, время начала/завершения, model/provenance unknown flags, generation parameters/seed если API поддерживает, prompt-template/version, system/application instructions, user prompt, видимый conversation history, tools/config/schema, retrieval revisions/excerpts, context/memory manifest, input/output hashes, обработку ошибок/повторов и validator verdict. API-ключи/Authorization никогда не входят в пакет; приватные материалы находятся в защищённом хранилище, не Git.

Не требуется получать скрытые внутренние рассуждения модели. Хранятся видимые структурированные факторы/обоснование, которые использовала программа. Только response ID недостаточен для replay, если тело впоследствии недоступно. Если провайдер не раскрывает фактическую версию за alias, это фиксируется как предел воспроизводимости, а не выдумывается номер сборки.

Повтор того же API-запроса сегодня — новый эксперимент с новым временем, возможной другой версией и недетерминизмом. Даже при одинаковом model string и температуре0 он не заменяет exact replay. Исходный результат/политика/оценка не перезаписываются более удобным повтором.

Проспективный commit завершён до целевого исхода/окна: время начала запроса ИИ не является временем фиксации решения. Если исход уже случился, пока модель отвечала, прогноз не маркируется проспективным для этого исхода. При неизвестной последовательности из-за часов/задержек `temporal_validity=unknown`, а не PASS. Окно будущей цены привязывается к commit; observed event time и время его поздней доставки различаются. Модель/контекст могут обновляться между будущими решениями, но каждая версия и дата её активации фиксируются; прошлое не меняется.

## 8. T2-C07 — ограничения статистики и продвижения

Отчёт группирует метрики по mode, data basis, execution model и temporal grade. Нельзя объединять условную историческую реконструкцию, современные LLM-прогоны истории и prospective в один показатель «точность без подсматривания».

`llm_historical_exploration` может породить кандидатную гипотезу, но не считается подтверждением её OOS-способности. Преимущество кандидата сначала проверяется на отложенном наборе, которого разработчик/подбор параметров не использовал, с учётом возможностей временно корректной оценки выбранного алгоритма; для современной LLM решающая проверка её рекомендаций — новые, заранее фиксированные будущие решения. Нельзя выдать окно, уже просмотренное LLM/аудитором при подборе, за независимое будущее. Полезность deterministic baseline оценивается отдельно.

Ни один режим не повышает `conditional/scenario execution` до observed fill. Правильная temporal discipline устраняет один класс ложных выводов, но не доказывает реальность исполнения, причинность и стабильность доходности. Процедуры приостановки/отката после продвижения применяются отдельно; temporal breach уже работающей версии должен поступать в техническую/модельную диагностику и протокол безопасности.

## 10. Ответ по замечаниям и точки интеграции

В общих документах требуется: заменить универсальный backtest-фильтр в data-model на mode-specific eligibility; добавить PublicationAvailabilityClaim/ContextManifest/TemporalValidityAssessment; включить isolation boundary в architecture; в sources указать недоказанную публикацию старых daily revisions; разделить evaluation modes в economics/implementation-plan; занести model knowledge и unknown public timestamps в risks/open questions; добавить критерии выше в acceptance-tests.
