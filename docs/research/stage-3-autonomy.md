## Исправление архитектуры

Ранее `knowledge-watch` обслуживал обновление публичного каталога. Это оставляло ручные команды импорта единственным способом обновить локальные знания. Добавлен [LocalKnowledgePoller](../../wow_auction/knowledge_local.py), подключённый основным исполнителем к `knowledge-watch`/`knowledge-update`: локальные SavedVariables проверяются автоматически до сетевого обновления источников. WoW может быть закрыт; обработка уже сохранённых файлов и публичного каталога не требует его запуска.

Poller использует только пути действующей локальной конфигурации: `TradeSkillMaster.lua`, `CraftSim.lua` и собственный `WowAuctionBridge.lua` рядом с ними. Он ничего не вызывает в игре и не записывает в WoW. Установленный build определяется по активной записи Retail в `.build.info`; отсутствующий/противоречивый build даёт unknown. Build настроенного импорта не приписывается старым cache rows как время и версия их наблюдения.

Каждая успешная новая запись обрабатывается после двух согласующихся чтений. Между изменениями проверяются inode/размер/mtime; не реже чем через 300 секунд по умолчанию повторяется проверка bytes/hash, даже если metadata файла совпадает. Ошибка одного источника не удаляет его прежнюю историю и не мешает прочим источникам. Повтор и перезапуск используют ту же identity `raw SHA + normalizer revision + build`, что ручной диагностический импорт: первая payload/receive сохраняется, одинаковый файл не создаёт новые наблюдения.

Четыре независимых вида артефактов:

| Вид | Что обрабатывается автоматически | Что не утверждается |
|---|---|---|
| `item_metadata` | Локальный TSMItemInfoDB: имена, source item keys, уровни, флаги и прочие известные поля | Торгуемость физической вещи и полнота всех предметов |
| `tsm_crafting_cache` | Сохранённые craft strings, материалы, выходной item string, numResult, cooldown flag, категория | Свежая точная схема, одновременно выбранные альтернативные реагенты, PMF |
| `craftsim_cache` | Версионированные item↔recipe связи, cached recipe/operation/profession info, gear/spec/concentration/cooldowns, очередь/настройки и сохранённые себестоимости, когда они существуют | Новый запуск расчётного движка, свежесть личных характеристик, исполнение очереди |
| `craftsim` | Собственный сохранённый export, включая расчётные profiles и отдельные passive observations, если они есть | Свежая персональная оценка там, где экспорт устарел, неполон или ещё отсутствует |

Названия персонажей не нужны для глобального discovery. В разделе crafter cache они заменяются устойчивыми локальными hashes. Сами артефакты остаются в приватной локальной БД; отчёт содержит counts/hashes, не полный cache. Чужие SavedVariables и рабочие БД активов/рынка не изменяются.

## Подтверждённые ограничения форматов

В установленном TSM `Core/Service/Crafting/ProfessionScanner.lua:67–68` записывает `numResult = floor((min + max)/2)`. Даже целое значение — усечённая середина диапазона источника, не гарантированный физический выход и не PMF. `Core/Service/Crafting/Core.lua` сохраняет `mats`, `itemString`, `numResult`, `hasCD`, `rootCategoryId` и сведения о крафтерах. На реальных57 записях встречены material prefixes `i`, `q`, `f`, `o`, `r`; они сохранены как исходные mat strings. Альтернативные quality/optional/finishing slots не развёрнуты в одновременное потребление всех перечисленных предметов.

`CraftSim/DB/crafterDB.lua:19–29,157–203` описывает и сохраняет перечисленные recipe/operation/profession caches; `lastCraftingCostDB.lua:11–13` определяет cost как **среднюю себестоимость предмета в меди** и отдельный timestamp. В исследованном текущем файле таких cost rows нет. Hashes этих первичных файлов и актуальных SavedVariables находятся в JSON. Неизвестная версия отдельного репозитория остаётся `unsupported_schema`, а не трактуется как совместимая.

Пассивный аддон может добавлять доступные локальному клиенту схемы самостоятельно в обычной игровой сессии; разработка этой части выполняется отдельным адаптером и не требует действий пользователя с конкретным рецептом. Недоступный игровой API или закрытая игра означают ожидание нового обычного сохранения, а не необходимость ручного задания для пользователя. Свежая личная полнота не гарантируется и не заменяется предположением.
