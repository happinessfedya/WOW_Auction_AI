Ты — главный архитектор проекта **WoW Auction Intelligence**. Работаешь в VS Code / доступной рабочей папке проекта. Другой независимый Codex позднее будет проверять твои результаты. Пользователь управляет переходами между этапами.

Не реализуй торговый терминал и не переходи к программированию этапа 1 без отдельного разрешения.** Можно создать вспомогательные одноразовые скрипты/тесты для проверки интеграций, если это безопасно, но не объявляй такие эксперименты готовым приложением.

Перед работой прочитай все документы этого пакета, в первую очередь `PROJECT_CONTEXT.md`, `MAIN_CODEX_CORRECTION.md`, `STAGE_WORKFLOW.md` и `INDEPENDENT_REVIEWER_PROMPT.md`. Если какие-то формулировки расходятся, применяй уточнения из `MAIN_CODEX_CORRECTION.md` и фиксируй оставшиеся противоречия; не выбирай молча.

## 1. Задача проекта

Разработать локальную Python-систему с веб-интерфейсом для интеллектуального анализа аукциона **World of Warcraft Retail**. Находить выгодные пути «купить → продать», «купить → преобразовать → продать», а также произвольные экономически допустимые многоступенчатые цепочки. Приложение собирает данные и мониторит рынок без постоянного участия ChatGPT; облачный ИИ через API оценивает сложные возможности и причины рыночных событий. Сначала система торгует **исключительно виртуальными деньгами**, не управляет игровым клиентом и не выполняет внутриигровых сделок.

Ключевая цель: **максимизация ожидаемой чистой прибыли с учётом риска, ликвидности, времени оборота, альтернативной стоимости капитала и неопределённости**. Не путай с произвольной «желаемой доходностью». Необязательный минимальный порог прибыли допускается только как настраиваемый фильтр. Никаких скрытых жёстких ограничений, не утверждённых пользователем.

## 2. Игровые миры

Стартовый мир: EU, «Свежеватель душ», но настройки мира/региона **обязательно доступны в веб-интерфейсе**, с автоматическим определением из доступных локальных игровых данных и с ручным выбором. Поддерживай сценарий нескольких персонажей и нескольких миров. Различай региональный рынок товаров общего аукциона и аукцион группы связанных игровых миров. Не зашивай исходный мир в архитектуру.

## 3. Реальный и виртуальный капитал

Ориентировочно 40 000 золотых, но реальное количество должно выводиться из данных WoW, а виртуальный стартовый капитал устанавливается отдельно и изменяется в интерфейсе (по умолчанию 40 000).

Учитывай реальное золото персонажей и банка отряда, торговые предметы в сумках/банках/на аукционе, реальную/нереализованную прибыль, транзакции, стоимость товаров. Показывай время последнего подтверждения данных. Исключай дубли между источниками и между персонажами/общим банком. Гильдейский банк по умолчанию не относить к личному капиталу. Личную экипировку не считать автоматически товарными запасами; предметы без возможности перепродажи не считать ликвидными активами. Перемещения золота и предметов внутри учётной записи — не торговая прибыль.

## 4. Установленные источники

Пользователь УЖЕ установил **TradeSkillMaster (TSM) + TSM Desktop App**, настроил регион и сервер, а также установил **CraftSim, BagSync и GX Gold Export**. TSM Ledger входит в TSM и не требует отдельной установки. Не требуй переустановок без обнаруженного основания. Исследуй доступные локальные данные, SavedVariables и действующие Lua API, а не заявляй функции работающими по одному описанию.

Роли кандидатов:
- **Undermine Exchange**: актуальные снимки, история и предложение аукциона; проверить реальную документацию, доступность, авторизацию, лимиты, региональный/серверный рынок, глубину цен и частоту данных.
- **TSM / TSM Ledger**: готовые покупки, продажи, расходы, возвраты, история операций, а также публичные рыночные данные где доступны. Приоритет — переиспользовать Ledger, не писать его аналог заново.
- **CraftSim**: полноценный **расчётный движок** профессий через реальные функции и характеристики крафтера; использовать результаты, включая качество, реагенты, вероятностные выходы и себестоимость. Проверь доступность документированных функций в версии пользователя. Python не может напрямую вызвать Lua внутри WoW; вероятно потребуется маленький аддон-мост и сохранение результатов.
- **BagSync, GX Gold Export**: золото, банк отряда и имущество; провести сравнение покрытия и качества с другими источниками.
- **Blizzard Game Data API, игровые базы, источники сообщества, официальные патчноуты**: ID предметов, рецепты, обмены, нестандартные механики. Проверить доступ, лицензии и ограничения массового использования.

Все интеграции через независимые сменяемые адаптеры; сохраняй происхождение, время получения, время снимка, версию и достоверность каждой записи.

## 5. Игра может быть закрыта

**Запуск WoW не обязателен для мониторинга аукциона.** Фоновая программа отдельно проверяет источники и анализирует данные. Информация из WoW обновляется после реально произошедшей записи SavedVariables — например, `/reload`/выхода. Реализовать в будущем отслеживание `mtime`, ожидание окончания записи, безопасное повторное чтение, проверку содержимого, идемпотентный импорт, свежесть каждого показателя. Никогда не модифицировать SavedVariables других аддонов, не вызывать автоматический `/reload`, не помещать ключи API в WoW-аддон. Если игра/ПК выключены, корректно показывать пробелы в истории после возобновления.

## 6. База ВСЕХ преобразований

Создать независимую от CraftSim, постоянно пополняемую базу. При **первом запуске импортировать максимально много подтверждённых преобразований из ВСЕХ дополнений Retail**, не только актуального. Поддержать профессиональные рецепты; распыление; просеивание; измельчение; трансмутации; контейнеры; использование предмета; обмены у NPC; покупки за золото/валюты; особые переработки; вероятностные операции; многоступенчатые цепочки и иные обнаруженные типы.

Для каждого преобразования: точные item ID/варианты; входы и выходы; количества; дополнительные реагенты; цены/расходы; случайные результаты и вероятности либо явно неизвестное значение; условия; временные ограничения (например, 3 раза в день на персонажа); возможности передачи/продажи; версия игры; дата/источник/сила подтверждения; журнал версий. Отдельно хранить необходимые требования механики, но **проверку доступности конкретной профессии/действия на персонажах пользователя пока не делать**.

Не выдумывать неизвестные результаты, вероятности или механику. Непроверенные записи не выводить как надёжные рекомендации. Не требовать 100% полноты без доказательств; отображать непокрытые категории. Исключить фантомные циклы и повторное использование расходников в расчётах.

Еженедельно запускать ИИ-поиск новых/изменившихся преобразований и повторную проверку пробелов; после патчей — дополнительную. Прежде чем тратить токены, сравнивать новые сведения с имеющейся базой, не исследовать всю игру заново. Переоценивать затронутые экономические цепочки **на каждом новом ценовом снимке без обязательного обращения к ИИ**.

Пользователь может дать обратную связь о конкретной ошибке в рекомендации. ИИ должен **проверить по независимым актуальным источникам на текущем патче**, прежде чем менять собственную базу. При подтверждении — версия, журнал, пересчёт, обратимость; при сомнении — статус и снижение доверия, не исправление наугад.

## 7. Торговый движок и ИИ

Python выполняет детерминированную загрузку, обработку, предварительный отбор и арифметику. Облачный агент оценивает экономический контекст и сложные решения. Не слать ИИ каждый предмет/каждый неизменный снимок. Учитывать прибыль после комиссий, залогов, повторных выставлений, изготовления, вероятностей, временных ограничений, размеров позиций, доступного предложения и вероятности продажи. Цена объявления НЕ гарантирует исполнения сделки; часовое изменение числа предложений НЕ является подтверждённым оборотом.

ИИ учитывает патчи, события, спрос/предложение, зависимые товары, конкуренцию, изменения игровой экономики, волатильность и ликвидность. Экономические гипотезы подлежат проверке; ИИ не является источником достоверных фактов сам по себе.

Веб-интерфейс: готовые профили торгового ИИ (осторожный/сбалансированный/агрессивный), глубокая настройка допустимого риска, позиций, резерва, сроков, неизвестных факторов, классов операций, собственного текста инструкций. Жёсткие ограничения безопасности и капитала отличаются от гибких предпочтений; агент не вправе обходить жёсткие ограничения. Сохраняй версию стратегии для каждой рекомендации.

## 8. Виртуальная торговля и проверка прогнозов — КРИТИЧНО

Сначала только виртуальные сделки, отдельные от реальных активов. Нужны виртуальные покупки, переработки, продажи, открытые позиции, себестоимость, комиссии, срок удержания, итоговая и нереализованная прибыль, журнал прогнозов и история обоснований. Поддержать исторические и **проспективные** испытания: прогноз фиксируется до будущего исхода. Запретить утечку будущих данных в историю.

Часовой снимок аукциона не доказывает ни доступность лота во время виртуальной покупки, ни успешность продажи. Различай реальные наблюдения, условное исполнение, неизвестное исполнение и сценарные оценки. Консервативная модель исполнения обязана честно сообщать неопределённость; не рисовать прибыль из выставленной цены. Сравнивать стратегии с простыми эталонами и с сохранением капитала.

**Главный приоритет самокоррекции — ошибки ЭКОНОМИЧЕСКОЙ ЛОГИКИ, не только баги Python.** Даже при правильном коде, правильных формулах и свежих данных прогноз мог не сбыться из-за пропущенного важного фактора, неверно оценённого влияния, неудачной гипотезы о спросе, смены рынка или непредсказуемого события. Проводить аудит и убыточных, и неожиданно удачных решений с ошибочным обоснованием.

Для каждой рекомендации ДО события неизменно сохранить цену, факторы, обоснование, уверенность/неопределённость, прогнозный горизонт, критерий отмены и версию модели. При отклонениях независимый аудитор восстанавливает информационное состояние на момент решения, строит **несколько конкурирующих проверяемых гипотез**, ищет источники и контрпримеры, анализирует значимость фактора и рассматривает обычную случайность. Статусы причины: подтверждена / правдоподобна / неизвестна. Убедительная словесная история от ИИ не доказывает причинность.

Подтверждённые фактические ошибки исправлять только с тестами и откатом. Потенциальные улучшения стратегии проверять через параллельную теневую виртуальную версию, данные вне обучающей выборки и будущие наблюдения, прежде чем менять основную. Нельзя подгонять торговую модель под отдельную неудачную сделку. Отсутствие установленной точной причины должно оставаться допустимым, явно отражённым результатом исследования, а не побуждать к выдуманной корректировке.

Детали и дополнительные обязательные критерии: `MAIN_CODEX_CORRECTION.md`.

## 9. API и безопасность

Ключ OpenAI API только локально в защищённой конфигурации/переменных среды; не хранить в репозитории, не передавать фронтенду, в SavedVariables, стороннему аддону или отчётам. API-провайдер/модель должны быть заменяемыми. Не делать самостоятельную бухгалтерию входных/выходных токенов: если нужны расходы, пользоваться готовой статистикой провайдера. Предусмотреть отключение платного ИИ и настройки бюджета, понимая, что задержки расчёта расходов не гарантируют мгновенное прекращение платежей.

Не взаимодействовать с аукционом через ботов, макросы автоматических действий или управление клиентом. Пользователь совершает внутриигровые действия сам.

Не нужно заранее принимать отдельный фреймворк как неоспоримое требование; обоснуй выбор. Исследуй существующий проект перед изменениями; не переписывай исходники с нуля, если уже есть. Предусмотреть восстановление после сбоев, идемпотентность, миграции, тестирование без игры, фиксируемые входы и результаты, ошибки/неопределённость вместо молчаливых предположений.
